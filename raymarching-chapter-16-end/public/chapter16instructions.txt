WHY ARE SAVING AND LOADING INTERFACES SO TERRIBLE?

You only need to build it once and people often treat it as an afterthought. But saving player progress is one of the most important parts of your game. You can probably think of a game you stopped playing because your save file got unintentionally wiped, or because saving and loading was tedious.

Godot has several built-in mechanisms for saving and loading.

SAVING GAMES: ALL THE POSSIBLE OPTIONS

Here's the possibilities that I know about, though there may be more!

SAVE OPTION SUMMARY: THE CONFIGFILE CLASS

https://docs.godotengine.org/en/stable/classes/class_configfile.html

Remember cracking open the folder of a game you've been playing to edit its INI file so you can tweak settings like monitor resolution? This is that. But ".cfg" instead of ".ini", by convention anyway.

Godot writes to such a file with the ConfigFile class, a text format similar to what you've seen in the INI files of yore. You'd use it to write a super basic text file with what is usually a long list of settings, like monitor resolution, UI size, and so on. The convention is a lowercase ".cfg" extension. (For obsessive readers, and to get Claude to stop harrassing me about this, file extensions are deployed in lowercase letters but often discussed in writing like this using CAPITAL LETTERS for readability.)

It's usually reserved for precisely that kind of thing. These CFG files are not only human readable, but typically lack any kind of hierarchical formatting or coding like you might see in a JSON file (or an HTML file if you're more familiar with those). These CFG files invite the user to go in and make changes themselves, perhaps because the game has stopped launching with a visible resolution, or it's showing up on the wrong monitor, or using the wrong driver, and so on. They often avoid private data so they can be uploaded for bug reports.

Nothing's stopping you from shoving other kinds of data into it, but it would be weird. I won't use it here, but I said I'd mention everything.

SAVE OPTION SUMMARY: FILEACCESS WITHOUT JSON

https://docs.godotengine.org/en/latest/classes/class_fileaccess.html

The FileAccess class is a conventional way of saving and opening pretty much anything. It can write anything, text, or binary, organized or disorganized. Floats, for example, will write as binary by default, which you won't enjoy reading.

SAVE OPTION SUMMARY: FILEACCESS, ORGANIZED WITH JSON TEXT

https://docs.godotengine.org/en/latest/classes/class_json.html

You can use FileAccess and have it write a file that isn't binary: JSON. JSON, if you're entirely unfamiliar with it, has the vibe and simplicity of HTML without javascript or a heavily nested dictionary. JSON has no logic, it's just a bunch of keys and values, nested however you want. It has the vibe of very old-school html files where there is no javascript, and a web browser is able to load an elegantly formatted page without creating a security hazard.

Godot also handles the conversion in and out of JSON for you, so... you don't have to learn another language. You don't need to crack a book or video open about JSON to use it. Unless you have to write the formatting yourself, reading it is usually self explanatory. Yay!

Thus, although you *could* save a variable as-is, and write it straight to the hard drive with FileAccess, it's more common to stringify it into JSON and *then* write it to the hard drive with FileAccess. If you stringify it first, then you can open the file later in a text editor and read it to analyze for problems.

Storing things in JSON can also make things more accessible for modders. Not so much because the mods will be touching the JSON files your game makes, but more likely because they'll save data to their own JSON files, and your game will already have a mechanism for moving that data in and out of the game.

NOTE TO SELF: MOVE TO JSON SECTION:

Claude alleges (and I think he's correct) that Godot's JSON abilities support dictionaries, arrays, strings, floats, booleans, and the "null" shape. He also alleges that JSON refers to dictionaries as "objects" and floats as "numbers". I'm guessing Claude probably isn't hallucinating that.

SAVE OPTION SUMMARY: RESOURCESAVER

https://docs.godotengine.org/en/latest/classes/class_resourcesaver.html

This is arguably the most "Godot-native" method of saving a file, because it's capable of taking a bunch of variables and saving them into one file as a Resource, using a format that the other Godot scene files load and use already (.tres and .res). The .tres format is also human-readable text. ResourceSaver has a major security hazard, which I'll address below.

SO WHAT'S BEST?

I don't know nearly enough about game productions to have a qualified answer to this, but I didn't find the answer to be as obvious as others made it out to be, and others definitely made it out to be obvious. Broadly, most agree that ConfigFile is for the limited purpose I described above. Most agree that writing things in raw binary with FileAccess is best avoided.

So you'll see arguments for the other two contenders: 1. a JSON file with FileAccess or 2. using ResourceSaver.

Saving things as a resource has the obvious advantage that you can shove a ton of native Godot variables into one save file with minimal effort. If you're an indie dev making a small game, that's probably fine, but it comes with an enormous security hazard. ResourceSaver and its twin ResourceLoader deal in .tres and .res files, so if a player loads someone else's save file or whatever, it can run code on their machine. 

JSON, on the other hand, is far more difficult to hide something nefarious in. Also, JSON is still often useful for things like multiplayer packets and modding. So I'm rolling with JSON.

AN ASIDE ABOUT GARBAGE COLLECTION AND REFERENCE COUNTING (SKIPPABLE FOR THOSE FAMILIAR)

All programming involves the creation of stored data, and erasing that data. Well, it's not so much "erased" as "freed" such that it can be replaced with something else.

With some programming languages, you have to manually write in when stored data needs to be freed, or... you literally just keep storing more and more stuff into perpetuity. Miss one thing anywhere, and you create what's called a "memory leak". This is why a lot of programs slowly slow down until they're immovable.

Some languages approach this problem with what's called "garbage collection", which is like a little janitor running around all the time, checking to confirm every variable is still in use by someone somewhere. And if it isn't, it gets nuked. The janitor moves intermittently; in gaming, this can mean the game slows down in moments of the janitor's choosing.

Godot handles (most) of that with a reference counting system. Godot tracks the number of references to a variable. If three nodes, or three scripts, or three whatevers refer to that variable's data, it stays live. Those nodes might get freed, or those scripts might conclude, or functions may finish, until the count hits zero. At that point, the data gets nuked. At least, when it's a reference-counted object and not a node.

The refcounted system, as far as I know, is separate from the node system. Nodes must be freed manually. This is why in a bullet-hell game you manually write code to queue_free() a fireball when it leaves the map so your game doesn't crash after five minutes and 10 million fireballs. Freeing is easy though because like with all Godot nodes, they follow the parent-child system, so freeing a parent frees the children.

What does this mean for you? Well, not tons. For the most part, it's a massive problem for people working in other languages that you can often ignore because it doesn't exist for you. That said, perhaps precisely because you almost never have to worry about it, it's easy to forget that you *sometimes* need to worry about it. You have to worry about freeing nodes, for example. It's also possible for two refcounted objects to refer to each other, and nothing else, and live on in unintended forever-ness, like a sad couple that stays together only because neither of them can tolerate revising their public persona on social media.

More often, you'll encounter tutorials or explanations online that refer to "RefCounted" like scripts that extend "RefCounted" instead of [insert node here]. Also, a script that doesn't say "extends" extends "RefCounted".

Pure code and logic and data and stuff that doesn't need to be in the node tree can live in RefCounted--once the counter hits zero of anything getting referred to it, it gets nuked. 

This is why there's two major-parent classes in Godot: Node and RefCounted. Nodes need to be freed manually and are generally reserved for what's on the scene tree. RefCounted is good for data that you want obliterated for you when things stop referring to it. In my bullet-hell game example, perhaps there's a RefCounted extension that's tracking how many bullets, how much damage given and taken, and a zillion other stats for that level, and you want that data to vanish on its own once the game stops referring to it. That's RefCounted.

You'll see both uses however--people who are experienced programmers will use RefCounted, whereas the inexperienced will often use Nodes for literally everything. Or just because. I, for example, created a Node in a game jam called "GlobalScripts" and to which I attached a "global_scripts.gd" script and which was an extension of "Node", just because it was a jam and I wanted everything visible in front of me. There's an entire UI in Godot for global scripts, but when you only have hours to make a game, you take shortcuts.

The data-only variables you're declaring within your scripts get nuked as part of Godot's refcounted sytem, but things you instantiate as nodes are not and must be freed manually.

I'm sure someone somewhere has written up a better summary of what these two systems are, but I didn't encounter it in my own reading.

Both of these inherit from Object, and there are siblings to RefCounted and Node that you've probably already seen, such as "Input" and "OS", along with less common engine ones like RenderingServer.

POPULATING THE LIST OF SAVED ITEMS WITH DirAccess

If you're wondering whether there's some Godot built-in that lists all of the files in a folder, yes, yes there is.

Replace the update_file_list function with this:

	func update_file_list():
		var packed_array_of_presets : PackedStringArray = DirAccess.get_files_at(PRESET_FOLDER)

A regular array can hold anything in its slots, whereas an Array that's typed as a string array by writing Array[String] is a less flexible array that holds only strings, and finally a PackedStringArray moves faster and uses less memory than all three but is the least flexible of the trio.

"Packed" shows up a lot in Godot, and it seems to mean pretty much the same thing everywhere--less flexible, more performant. One of the learning curves of Godot is just knowing which of the built-ins use them. Godot's designers seem to tilt toward making everything perform insanely fast, so, "packed" is rather common and it's best not to be afraid of it. In computer science, data travels in chunks of a specific size, everywhere, all the time, and "packing" means smashing those chunks together as tightly as you can in only one place. Like, pretend you're storing things in a box at home, and you're packing your kitchen utensils in a box. In some cases, you might know exactly how many utensils are going in, and pack them into adjacent boxes, and have them elegantly squished up next to each other within those boxes. But maybe you don't know, so you pack some of the utensils in a box, along with a piece of paper where you can write, "look in the red box in the attic for the rest of the kitchen utensils". Part of what makes a computer fast or slow is how often the programmer (or their engine) relies on the first method as opposed to the second. 

I read a lot of tutorials that mentioned Packed things, but nobody ever told me what it was, so in case you're like me I'm telling you now. Now you know. It's possible to speed up games by packing the data efficiently, but whether that makes a meaningful difference depends on the data and the game.

Add a for loop and a print command to the update_file_list function and make sure it's printing file names:

func update_file_list():
	var packed_array_of_presets : PackedStringArray = DirAccess.get_files_at(PRESET_FOLDER)
	for file_name : String in packed_array_of_presets:
		print(file_name.get_basename())

Claude suggested the "get_basename" method which may end up being what we want--it drops the extension off the file name. Claude also suggested a guard, "if file_name.ends_with(PRESET_EXTENSION):", which I left out. You don't really ever know where an operating system will shove a temporary file, so it's worth inserting the guard when I create a "clean" variable for the file list.

There's a very similar method, "get_extension()", which returns the extension.

The tldr: is that ends_with is inherently a test, a test that returns a boolean, based on whether the string you passed in is the grand conclusion of the string you called it from. Conversely, get_extension just returns the actual extension without a period. Use whichever floats your boat, but note that get_extension is case sensitive, and any tests you run with ends_with may also be case-sensitive, so, mind your cases. (I spent the first month of Godot failing at it because I was constantly failing at using capital letters in the right place, such as Node3D vs Node3d vs node3d.)

These are methods running on String variables, so there's not any witchcraft happening with files themselves.

Declare an array of legible file names, and iterate through the file names with a guard to protect against anything that doesn't end in .json :

	func update_file_list():
		var packed_array_of_presets : PackedStringArray = DirAccess.get_files_at(PRESET_FOLDER)

SUBSCRIBING THE SIGNAL 

We don't need to declare the signal for clicking on an item in an ItemList because the signal is a built-in. We just have to subscribe to it in the ready function:

	saved_settings_list.connect("item_selected", _shader_selected)

That signal spits out one thing (if you've forgotten the thing, hovering over the signal in the signal list tells you the thing) which is the index.

	func _shader_selected(index)->void:

The load shader function needs to do the following:

-Assign all the values to the LineEdits (this step doesn't yet trigger the values to update the shader)
-Apply those values to the shader

CONCLUSION

My understanding from other developers is that having a save game that is easy to read and edit saves a massive amount of time at... pretty much all stages of development. You can rig up a game that needs to be tested halfway through, create a zillion save files with slightly different tunings, read the results, and give a functioning save editor to your editors. It also forces the scope of what you're saving into something mercifully narrow.

What I find most interesting about this chapter: I never see shader editors showing up in player-facing UIs. Everyone just gets a color selector, and often, you're limited to a few color swatches. And yet: Players *obsess* over clothing and residence options for their characters. As this chapter shows, even as a beginner, you can expose shader-level details to the player, and you can still restrict those options to fall within useful boundaries.
