REFRESHING THE MEMORY

The last chapter, chapter 15, wired up the coefficients called for by Worley to an interactive UI using Godot's standard built-in controller/UI node system. But it left something important out, which was a means to save, load, and delete your favorite creations as you go.

WHY ARE SAVING AND LOADING INTERFACES SO TERRIBLE?

You only need to build it once and people often treat it as an afterthought. But saving player progress is one of the most important parts of your game. You can probably think of a game you stopped playing because your save file got unintentionally wiped, or because saving and loading was tedious.

Godot has several built in mechanisms for saving and loading.

SAVING GAMES: ALL THE POSSIBLE OPTIONS

Here's the possibilities that I know about, though there may be more!

SAVE OPTION SUMMARY: THE CONFIGFILE CLASS

https://docs.godotengine.org/en/stable/classes/class_configfile.html

There's the ConfigFile class, which saves things to an INI file. That's a very basic text file (with the .ini extension) with what is usually a long list of settings, like monitor resolution, UI size, and so on. 

It's usually reserved for precisely that kind of thing. These INI files are not only human readable, but typically lack any kind of hierarchical formatting or coding like you might see in a JSON file (or an HTML file if you're more familiar with those). These INI files invite the user to go in and make changes themselves, perhaps because the game has stopped launching with a visible resolution, or it's showing up on the wrong monitor, or using the wrong driver, and so on. They often avoid private data so they can be uploaded for bug reports.

Nothing's stopping you from shoving other kinds of data into it, but it would be weird. I won't use it here, but I said I'd mention everything.

SAVE OPTION SUMMARY: FILEACCESS WITHOUT JSON

https://docs.godotengine.org/en/latest/classes/class_fileaccess.html

The FileAccess class is a conventional way of saving and opening pretty much anything. By itself, it won't be something a person can read, because it writes in binary.

SAVE OPTION SUMMARY: FILEACCESS WITH JSON

https://docs.godotengine.org/en/latest/classes/class_json.html

You can use FileAccess and have it write a file that isn't binary: JSON. JSON, if you're entirely unfamiliar with it, looks like HTML or like a heavily nested dictionary. It's technically code, but there's no logic, it's just a bunch of keys and values, nested however you want. 

Godot actually handles the conversion in and out of JSON for you, so... you don't have to learn another language. Yay!

Thus, although you *could* save a variable as-is, and write it straight to the hard drive with fileaccess, it's more common to stringify it into JSON and *then* write it to the hard drive with fileaccess. If you stringify it first, then you can open the file later in a text editor and read it to analyze for problems.

Storing things in JSON can also make things more accessible for modders. Not so much because the mods will be touching the JSON files your game makes, but more likely because they'll save data to their own JSON files, and your game will already have a mechanism for moving that data in and out of the game.

NOTE TO SELF: MOVE TO JSON SECTION:

Claude alleges (and I think he's correct) that Godot's JSON abilities support dictionaries, arrays, strings, floats, booleans, and the "null" shape. He also alleges that JSON refers to dictionaries as "objects" and floats as "numbers". I'm guessing Claude probably isn't hallucinating that.

SAVE OPTION SUMMARY: RESOURCESAVER

https://docs.godotengine.org/en/latest/classes/class_resourcesaver.html

This is arguably the most "Godot-native" method of saving a file, because it's capable of taking a bunch of variables and saving them into one file as a Resource, using the same format that the other Godot scene files are written in (.tres and .res). The .tres format is also human-readable text. ResourceSaver has a major security hazard, which I'll address below.

SO WHAT'S BEST?

I don't know nearly enough about game productions to have a qualified answer to this, but I didn't find the answer to be as obvious as others made it out to be, and others definitely made it out to be obvious. Broadly, most agree that ConfigFile is for the limited purpose I described above. Most agree that writing things in raw binary with FileAccess is best avoided.

So you'll see arguments for the other two contenders: 1. a JSON file with FileAccess or 2. using ResourceSaver.

Saving things as a resource has the obvious advantage that you can shove a ton of native Godot variables into one save file with minimal effort. If you're an indie dev making a small game, that's probably fine, but it comes with an enormous security hazard. ResourceSaver and its twin ResourceLoader deal in .tres and .res files, so if a player loads someone else's save file or whatever, it can run code on their machine. 

JSON, on the other hand, is far more difficult to hide something nefarious in. Also, JSON is still required for things like multiplayer packets and modding. So I'm rolling with JSON.

GET THE READY FUNCTION TO CREATE THE FOLDER IF IT DOESN'T EXIST YET 

This requires use of the DirAccess class, short for "Directory Access".

	func _ready() -> void:

The Save button has quite a few things. What I laid out earlier:

	the save button needs to fire a signal to a handling function.
	the save file's handling function needs to write a dictionary that...
		consists of the text in each of the relevant boxes, and is

		stringifies the dictionary to a variable
		writes the now JSON dictionary to a new file

The save button needs to fire a signal that calls the save function. This means adding the save button to the long list of @onready variables. Add the load button and the save name LineEdit node while you're here:

	@onready var save_button : Button = $CanvasLayer/MarginContainer/HBoxContainer/SaveLoad/SaveButton
	@onready var load_button : Button = $CanvasLayer/MarginContainer/HBoxContainer/SaveLoad/LoadButton
	@onready var save_name_line : LineEdit = $CanvasLayer/MarginContainer/HBoxContainer/SaveLoad/EditSaveName

The save and load buttons need to call save and load functions. They have a signal built in for that. In case you've forgotten what that signal looks like, you can click the "SaveButton" node in the node tree in the top left panel of Godot, and then the Signals tab to the in the far right panel that's normally behind the Inspector tab. The signal is "pressed". So add a subscription to the _ready function:

	#Save/loading subscription below:
	save_button.connect("pressed", _save_shader)
	load_button.connect("pressed", _load_shader)

Those will show up in red until you add a stubs for each callable:

	func _save_shader()->void:
		pass
		
	func _load_shader()->void:
		pass

If you want to confirm you're subscription is working, toss in a print function:

	func _save_shader()->void:
		print("Save button pressed!")
		pass

NOW TURN IT INTO A JSON

This is surprisingly easy, just by adding this line:

	var jsoned_dictionary : String = JSON.stringify(dictionary_to_save, "/t", false)

The second argument is a tabbed indent which prevents the string from being one long hard to read line.

The third argument prevents JSON.stringify from automatically sorting things alphabetically. I don't want things coming back out in a different order than I put them in, though I'm not sure it matters.


IDENTIFYING A SAFE PLACE TO SAVE IT 

Already established up top was the folder and extension:
	const PRESET_FOLDER := "user://presets"
	const PRESET_EXTENSION := ".json"

And then the DirAccess code in _ready has already created that folder:

	_ready():

		#Stuff that happened a long time ago

		if not DirAccess.dir_exists_absolute(PRESET_FOLDER):
		DirAccess.make_dir_recursive_absolute(PRESET_FOLDER)

So now we just need a file name itself. Some stuff to deal with:
-The file name should come from the pretty name the user typed
-The name should be cleaned up in case it has slashes or whatever
-Things should abort if the file already exists (or add a number or something)

Strings have a "validate_filename()" method on them which cleans up strings and turns them into functional names. Thus:

	var file_name := save_name_line.text.validate_filename() + PRESET_EXTENSION

Strings also have a ".path_join()" method which allows you to cleanly marry path segments together, in this case, a directory location (the first segment) and the file name (the second segment).

	var full_path := PRESET_FOLDER.path_join(file_name)

As a sidenote, literally nothing about this is obvious or intuitive. I suspect 90% of Godot users look this up every time they do it or reuse old code. Here's the code to write the file:

	var file : FileAccess = FileAccess.open(full_path, FileAccess.WRITE)
	if file == null:
		push_error("The save_shader function ran into a problem with " + str(FileAccess.get_open_error()))
		return
	file.store_string(jsoned_dictionary)
	file.close()

Although as a beginner you'd just end up copying and pasting this every time, a few thoughts:
-You're creating an object with the FileAccess type.
-The word "open" might feel like a misnomer for creating a file that doesn't exist yet.
-Remember to close() the file, like saying goodbye to a Ouija board, or the file haunts you or something

Claude produced/alleges this helpful table in terms of what happens depending on what you initially tell FileAccess to do:

	Mode          If the file is missing      If the file exists
	----------    ------------------------    ------------------------------
	READ          fails, returns null         opens it for reading
	WRITE         creates it                  wipes it, then writes
	READ_WRITE    fails, returns null         opens it without wiping
	WRITE_READ    creates it                  wipes it, then opens it
