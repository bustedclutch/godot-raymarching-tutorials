Worley noise functions by measuring the distance from your current position to a point in a 9 cell cell neighborhood. (We expanded on it by playing with the coefficients of the various distances to points that were further out, but we can ignore that for now.)

There's a couple of contenders for how you could animate the patterns produced by Worley noise. And by animate, I mean really animate it, not just have the entire shader slide or spin or expand or shrink. We want the pattern itself to shift.

	CONTENDER 1: Directly moving the points themselves
	Although the points are stochastic, we could just slide them around within their cells by manipulating their coordinates before the distance function gets evaluated.

	CONTENDER 2: Adding a third dimension 
	The noise pattern could go from being a sheet of paper to a thick piece of balogna. And as time progresses, you slice further and further into it. 

	CONTENDER 3: Domain warping
	Alter the uv numbers before any of the Worley math runs. You just add a line like this after the uv_math helper runs:
		uv = uv+ 0.3 * sin(uv.yx * 2.0 + TIME);
	"Domain warping" is a glamorous phrase for "playing with the input before it gets fed into the bigger function doing most of the work".

	CONTENDER 4: Whatever else you discover/find/invent

The destination is raymarching, and raymarching is actively perceived in three dimensions as the viewer moves around the object. So I'm going to make an actual third dimension. Sometime down the road, I'll need to address how to fake a fourth, for animated smoke and clouds.

IS THIS EXPENSIVE?

This will take us from a nine cell neighborhood to a twenty-seven cell neighborhood. Like moving from a tic-tac-toe board to a rubic's cube. Is this expensive? If it's only run once, no. If it's run at every raymarching step, then... yes. But I'll worry about that later.

ADDING A THIRD DIMENSION

I'm just going to go through every reference to the X and Y dimensions, and make a rough plan for dealing with them.

ADDING A THIRD DIMENSION PART 1: THE CURRENT CELL IDENTIFIER 

The first mention is when the UV's is used to find the grid identifiers for the current position. That's this:

	uint uv_grid_id_x = grid_id_x(uv);
	uint uv_grid_id_y = grid_id_y(uv);

The first brain noodle is: How do we ensure that as UV's go up up up, that there's a Z dimension that has the same proportions? 

It's worth consulting the helper function, grid_id_x(), to see what kind of data that function receives, and what kind of data it spits out, so that we can play matchy matchy with the input and output, as well as the helper function that's doing uv math:

	uint grid_id_x(vec2 xy){
		float x_vec = xy.x;
		float x_floor = floor(x_vec);
		return uint(int(x_floor));
	}

	vec2 uv_math(vec2 xy, float local_scale){
		vec2 uv = xy;
		uv = uv * 2.0 - 1.0;
		uv = uv * vec2(1.0, -1.0);
		uv = uv * local_scale;
		return uv;
	}

The tldr; of this pipeline is that the UV, a number between 0 and 1, normalized to fall between -1 and 1, gets flipped, and then multiplied by a scale, which at the moment, is 3.0. The flipping isn't relevant. But to add a raw Z value, something based on TIME, location, or perhaps a smoothly flowing pseudorandom number, we will likely have to do two things to the raw Z value:
1. (Possibly) normalize the Z number to run -1 to 1, and 
2. (Possibly) scale Z it by the same number getting applied to the UV's.

I say possibly because it depends on where Z is coming from. In the event X and Y and Z are all coming from known locations in 3D space, we don't have to do any of this. So in that regard, the raymarcher version of this is easier. But for this chapter, I shoving a square peg into a round hole, and making some arbitrary Z value fit the vibe of the UV coordinates.

Matchy-matchiness will then hopefully be achieved.

ADDING A THIRD DIMENSION PART 2: Get the whole and fractional parts of Z

The shader currently evaluates where you (the current pixel) are within this line:

vec2 local_current_pos = vec2(fract(uv.x),fract(uv.y)); //Finds the local coordinate within the current grid cell

And it doesn't get the whole part of Z at all.

We'll need both; the whole part for the hash, and the fractional part for the distance math. We need to separate the 3.122523 into 3 and 0.122523.

 We can add a Z dimension as a third loop.

ADDING A THIRD DIMENSION PART 3a: The loop finds the test cell identifier

The for loop grabs the test cell's identifiers for all dimensions getting tested:

		uint cell_uint_x = uint(int(uv_grid_id_x) + local_x);
		uint cell_uint_y = uint(int(uv_grid_id_y) + local_y);

That's just a simple grab for Z with the same pattern.

ADDING A THIRD DIMENSION PART 3b: The loop finds a random local point using integers

	vec2 random_loc_p = random_local_point(cell_uint_x,cell_uint_y)

This one will actually get a little spicy, because it's a return to bitwise hashing. We'll need a new helper function that accepts three integers instead of two, and returns a vec3 instead of a vec2.

ADDING A THIRD DIMENSION PART 3c: Giving the point a neighborhood address instead of a local one

This code gave the point an address on the entire tic tac toe board rather than its xy location within an individual cell, by adding -1, 0, or 1. 

	random_loc_p.x += float(local_x);
	random_loc_p.y += float(local_y); 

A third line in the same format will do the same for the Z dimension, so this is another easy change.
